<p>被问得最多的一个问题不是"买哪家"，而是"IP 已经买了，接下来按什么顺序做"。顺序错了的典型后果是：先绑定再验证，发现 IP 根本不通，绑定表全废；或者先注册再想记录，一周后没人说得清哪个号在哪条线上。这篇按真实提问的顺序往下走，从"要不要先固定出口"开始，到"出问题先回滚哪一步"结束，每一步给出动作、完成判据和大致耗时，最后附一张可以直接抄的绑定表。</p>

<h2>一、注册前到底要不要先固定出口</h2>
<h3>要，而且要在注册前</h3>
<p>注册过程中产生第一条记录，这条记录里带着出口地址。如果注册时用的是临时线路，后面换成静态 IP，等于账号的第一次出现和后续所有出现都不在同一地址上。虽然不至于立刻出问题，但会多一层解释成本，没有必要。</p>
<h3>固定的含义是三层都不动</h3>
<p>IP 不动、出口所在城市不动、DNS 解析位置不动。只做到第一层的情况最常见：IP 换了，DNS 还在本地解析，实际暴露的位置没变。三层一起固定，才算真的固定。</p>

<h2>二、拿到静态 IP 之后，第一步该验什么</h2>

<h3>先验通，再验归属，最后验稳定</h3>
<p>顺序不能反。先 curl 确认能出去，再查归属是不是 ISP 段，最后连续测一段时间的稳定性。跳过第一步直接查归属，可能出现"归属很好但根本连不上"的尴尬。</p>
<h3>三步的具体命令</h3>
<p>第一步：curl -x http://用户:密码@主机:端口 -s https://ipinfo.io/json，看 ip 是否等于分配给你的地址。第二步：whois 该 IP，看 netname 与 orgname 是否运营商；再在 ipapi.is 查 asn.type 是否为 isp。第三步：连续 100 次请求，统计失败次数与 p95 首字节，顺手 dig -x 取 rDNS 存下来。</p>

<h2>三、浏览器怎么绑这条线才不串</h2>
<h3>绑定发生在配置文件层</h3>
<p>不要用系统级代理，系统级代理会让所有浏览器窗口都走同一条线。正确做法是给每个配置文件单独设代理，在启动参数里指定，或用支持按配置文件配代理的浏览器。命令行方式：chrome --proxy-server="http://主机:端口" --user-data-dir="配置目录"，启动参数和配置目录一起固定下来。</p>
<h3>带鉴权的写法</h3>
<p>命令行参数不方便带账号密码，通常用扩展或本地转发端口解决：本地起一个小端口转发到上游代理并附带凭据，浏览器只连本地端口。这样密码不进启动参数，也不会出现在进程列表里。</p>
<h3>绑完立刻自检三项</h3>
<p>打开 ipinfo 看出口、打开 ipleak 看 DNS、看浏览器语言是否为该地区常用语言。三项都对，再开始登录。任何一项不对，先修再登，别抱着"先试试"的心态。</p>

<h3>表放哪、谁能改</h3>
<p>放共享文档，开修改记录。两人以上维护时，规定只有一个人能改状态字段，避免同时编辑互相覆盖。这张表看起来是行政工作，实际上是排障时唯一的事实来源。</p>

<h2>五、中途出问题，回滚顺序是什么</h2>
<h3>从最外层往回退</h3>
<p>先退浏览器操作（停手、关标签），再退环境改动（恢复上一次的配置备份），再退出口（切回上一条验证过的线），最后才考虑改账号资料。顺序反了会把一个可恢复的问题变成两个。</p>
<h3>什么情况下不要回滚</h3>
<p>只是偶发一次验证、且近期没有任何变更时，回滚等于主动制造变化。此时正确动作是保持现状、放慢节奏、观察两三天。判断依据还是那句：看变化幅度，不看单次提示。</p>
<h3>回滚之后必须补记录</h3>
<p>在绑定表里加一行变更记录：时间、改了什么、为什么改、结果如何。没有这一行，下次遇到同类问题还要重新推一遍。</p>

<h2>常见问答</h2>
<h3>静态 IP 到手后可以先登录再验证吗？</h3>
<p>答：不建议。先验证再登录，能避免在一个有问题的环境里留下登录记录。验证只需要半小时，返工的成本要高得多。</p>
<h3>一个配置文件能切换两条线吗？</h3>
<p>答：技术上可以，但不建议。同一环境在不同出口之间来回切，等于反复制造变化。需要多地区时，用多个配置文件，各自固定一条线。</p>
<h3>绑定表要不要记密码？</h3>
<p>答：不要。密码放密码管理器，表里只放账号标识与出口信息。表一旦泄露，损失会从"知道你在用哪条线"扩大到"能直接登录"。</p>
<h3>换了 IP 之后多久能恢复正常？</h3>
<p>答：取决于变化幅度和账号状态，通常几天到两周。这段时间保持节奏稳定、不做批量操作，比频繁调整更有效。</p>
